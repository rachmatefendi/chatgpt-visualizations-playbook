# Contributing

Thank you for your interest in improving this independent reference by Rachmat Efendi.

## Before proposing a change

- Link the precise official documentation passage for claims about native or documented capabilities.
- Label every component or format **V**, **K**, or **P**; do not silently promote patterns to official Visualizations components.
- Use fictional or properly authorized data; remove secrets, identifiers, and privileged documents.
- A new use case must include a decision question, source/data contract, interaction rules, sample prompt, acceptance tests, failure modes and an authority boundary.
- Financial results require definitions, dated cash-flow inputs if appropriate, transparent assumptions, and independent checks.
- Do not include executable code marketed as an official private Visualizations renderer or SDK.

## Propose an update

Describe the changed document, objective, evidence/source date, proposed delta, validation procedure and any compatibility effects. Keep scope targeted; do not reopen accepted content without a material change.
